# Currency Magnitude Census — 2026-07-29

Program 27 spec §6.1 asks: how large do `Currency` values actually get in
shipped artifacts, and does that support the proposed i64-micro-unit overflow
claim / i128 headroom pin? This report is the evidence; the pinned assertions
live in `tests/unit/kernel/test_currency_magnitude_pin.py`, generated by
`tools/currency_magnitude_census.py`.

## Method

`tools/currency_magnitude_census.py` walks three sources for the largest
`abs(value)` numeric leaves, with provenance:

1. Every JSON file in `tests/baselines/*.json` (recursive walk of all
   dict/list leaves — not currency-typed-field-aware, so this is a superset
   census; non-finite leaves, e.g. an `Infinity` from a divide-by-zero
   `dependency_ratio`, are excluded as data artifacts, not currency values).
2. Every dense CSV golden in `tests/baselines/dense/*.csv`.
3. Every `REAL`/`INTEGER`/`NUMERIC`/`FLOAT` column's `MAX(ABS(...))` in the
   reference DB (`data/sqlite/marxist-data-3NF.sqlite`), when that
   (gitignored, build-product) file is present.

Run against a fully LFS-hydrated checkout with the reference DB built
(`/home/user/projects/game/babylon`, main checkout — the Phase-0 worktree
this census was authored in lacked both the hydrated `michigan-e2e.json` LFS
blob and the reference DB, so the tool degrades gracefully: it skips
un-parseable JSON with a stderr note and skips the sqlite leg entirely if the
file is absent, rather than crashing).

## Ceiling arithmetic

```
I64_MICROUNIT_CEILING  = 2**63 / 1e6   ≈ 9.223372e12
I128_MICROUNIT_CEILING = 2**127 / 1e6  ≈ 1.701412e32
NATIONWIDE_SCALE_HEADROOM = 1_000       # tri-county/83-county Michigan -> ~3,100 counties + growth
```

* **i64 microunits at nationwide scale:**
  `2.4e13 * 1000 = 2.4e16 > 9.223e12` — overflows, as the spec's B2 claim
  states.

* **⚠ i64 microunits already overflow at CURRENT scale, no scale-up needed:**
  `2.4e13 > 9.223e12`. The 83-county Michigan fixture's largest accumulated
  value (`total_phi_inflow`) *already* exceeds the i64-microunit ceiling by
  itself — roughly 2.6× over, with zero nationwide multiplier applied. This
  is a **stronger** finding than the spec's stated 10–100× nationwide-scale
  margin: the overflow risk is not a future nationwide-scale concern, it is
  present today in the largest existing test fixture's accumulated flow
  totals. Whether `total_phi_inflow` (an events-payload aggregate, not
  necessarily itself typed as a single `Currency` micro-unit field in the
  engine) is representative of what actually gets stored/serialized as
  micro-unit `Currency` is a §6.1 re-derivation question for the Director —
  flagged here per Step 3 of the Task-4 plan, not resolved by this report.

* **i128 microunits at nationwide scale:**
  `2.4e13 * 1000 * 1e6 = 2.4e22 < 1.701e32` — comfortable headroom (~10
  orders of magnitude), confirming the i128 pin has ample margin even under
  the stronger current-scale-overflow finding above.

## Conclusion

1. The i64-micro-unit overflow claim (spec B2) holds, and by a wider margin
   than originally framed: overflow is observable **today**, in the largest
   shipped test fixture, without any nationwide-scale multiplier.
2. The i128-micro-unit headroom claim holds with ~10 orders of magnitude to
   spare even after applying the 1000× nationwide-scale headroom on top of
   the already-overflowing current-scale max.
3. **Flag for §6.1 re-derivation (Director):** confirm whether
   `total_phi_inflow` — an events-payload accumulated flow, not a single
   `Currency`-typed node field — is the correct basis for the i64/i128
   ceiling comparison, or whether the census should be narrowed to fields
   actually declared `Currency` in Pydantic models. The census tool as
   written is deliberately a superset scan (all numeric leaves) rather than
   a `Currency`-type-aware scan, per the plan's Step 1 script; narrowing it
   is future work if the Director wants a tighter bound.

## Tooling notes

* `tools/currency_magnitude_census.py` degrades gracefully when the
  reference DB (`data/sqlite/marxist-data-3NF.sqlite`, gitignored build
  product, ADR098) is absent, and when a baseline JSON is an un-hydrated
  git-lfs pointer (as `tests/baselines/michigan-e2e.json` was in the
  Phase-0 worktree this report was authored from) — both cases are skipped
  with a note rather than crashing, so the tool and its pinned test stay
  runnable in any worktree/clone. This report's authoritative top-50 was
  generated against the main checkout (`/home/user/projects/game/babylon`),
  which had both the hydrated LFS blob and the built reference DB.
